# 用户明确提出的主张、约束与纠正

本文件记录用户在这组 proposal 对话中明确提出、追问或纠正的要求。它们是写作与研究设计约束，不是论文事实。未来调用时优先服从用户当次的新要求；若冲突，以最新明确指令为准。

## 1. 交付物与文件治理

- 按用户提供的 `january proposal.docx` 格式生成正式 Word，不自行发明另一套格式。
- 正式 proposal 与解释性 Markdown 必须内容一致；用户质疑“为什么要分两个文档”，因此不能默认强制拆分。若保留两份，必须明确：Word 面向正式提交，Markdown 面向选题论证、术语解释、导师谈判与证据边界。
- 用户要求写入原有 Topic 对应文档时，更新现有权威 Markdown，不新建相似文档。
- 对既有多份 Markdown 的共同问题要全部扫描和同步修正，不能只改被点名的样例。
- Markdown 必须参考现有版本，保留已经核实的内容和结构，不从空白重写而丢失历史论证。
- 文档必须使用简体中文。

## 2. Topic 范围与选题方式

- Topic 必须明确体现 Agent、多模态和大模型分别在哪里，不能只在标题中出现三个词。
- 用户要求解释“为什么选择这个 Topic”，不能只描述 Topic 做什么。
- “再来几个 Topic 给我选”意味着提供机制和研究对象真正不同的方向，而不是对同一方向换标题。
- 每个候选应说明核心科学问题、首个决定性实验、3–5 年递进空间、kill/stop gate，以及可选的 LCCA 联系。
- 教育不是选题限制，只是一个应用场景。不能从“要服务教育”反推 Topic 并把研究限定成教育技术。
- LCCA 不能成为思路来源的边界。Topic 可以由 LCCA 的一个具体错误传播或工作流产生部分灵感，也可以在 LCCA 中练习某些组件，但通用问题、方法、benchmark 和主要验证必须独立于 LCCA。
- 与 LCCA 的联系要写成完整推导：从 LCCA 的具体例子发现问题，抽象成通用科学问题，再回到 LCCA 或其他场景做有限验证。
- 对 PolyU Education 4.0 的帮助必须回到具体学生、教师、评价或治理场景和指标，不能停在“个性化、智能化”口号。

## 3. 三至五年价值与时间线

- 必须详细说明为什么值得做 3–5 年、为什么未来 3–5 年仍可能受到关注，并提供调查或论文依据；不能靠“领域很热门”支撑。
- 时间线必须解释其科学意义和依赖关系，而不是简单把工作摊到年份。
- 用户明确否定“用一年建立 5–10 个只读探针”这种松垮计划。基础探针和配对 pilot 应在前 8–12 周完成，第一年必须进入强基线、序贯选择、诊断—恢复闭环和至少一次迁移。
- 3–5 年不是承诺每年都继续同一方法；任何核心命题失败都应缩小或停止相应路线。

## 4. 科学问题而不是工程包装

- 核心科学问题至少包含三个可独立推翻的命题。
- 必须详细防御“这是工程排障、日志管理或自动维护，不是科研”的质疑，并在可能时给出论文依据。
- 不仅写系统模块，还要说明现象是否存在、什么条件下可识别、什么策略优于强基线、诊断信息能否转化为恢复或决策收益。
- 现有论文怎样支持、又怎样限制选题必须逐篇讲清；不能只列论文名或用读者看不懂的专有名词概括“剩余空间”。
- 跨模态因果证据溯源与干预式故障诊断究竟是两个 Topic，还是同一 Topic 的前后步骤，必须明确。用户倾向把“来源依赖证据推理”和“主动验证／干预式诊断”连接成更高层闭环。
- “干预式”必须解释清楚：主动改变被怀疑的机制并观察后果；重新截图或读 DOM 可能只是主动观测。用户要求解释术语，不等于授权随意改掉原术语。
- 如果“干预式”作为唯一方法太窄，不足以支撑 3–5 年，应提升总立意；干预可以降为主动验证的一类方法。
- 需要准备至少 20 个 high-level challenge，供与博导谈判；应写入原有 Topic 文档，不额外创建零散文件。

## 5. 术语与来源

- 所有会影响论证的名词都应解释，不能假定读者知道 evidence state、identifiability、oracle、provenance、repair debt、shadow mode 等。
- 必须说明一个词是标准术语、某篇论文的专用定义、本文工作性定义，还是解释性类比。
- 如果论文已定义，应引用其原始定义和来源；如果是助手归纳，应明确写“本文定义”，解释它由哪些已有概念组合而来，不能把归纳包装成公认理论或首创。
- 用户曾以“证据状态”为例指出文档中存在未解释的专有名词；这个例子表达的是**所有影响理解的专业词都必须解释**，并不表示用户对“证据状态”提出了特殊理论主张，也不能由此推断用户要求采用某一种拆分或形式化方案。

## 6. 文献调研与 Undermind

- 用户要求用 Undermind 对 Word 和 Markdown 中提及的论文、Topic 现状做深入调查，并把结果更新回对应 Markdown。
- 不能因为 Undermind 或任何单一系统没有搜到论文就宣称“完全调研清楚”或证明新颖性。
- 必须说明检索边界和遗漏风险：术语不一致、相邻学科、索引延迟、低可见度论文、未公开工作和付费全文限制。
- Undermind 的优势主要在语义检索、引文扩展、工作区组织和并行全文提取；它不能绕过 IEEE 等付费墙或登录权限，也不能自动保证检索完整。
- 如果 PDF 已合法可用，Undermind 可提高并行全文问题提取效率；与直接阅读的差别主要是搜索和编排效率，不是更高的天然事实权威。重要论文仍要核对全文、图表、附录和正式 venue。

## 7. 个人优势

- “为什么我做起来有优势”必须具体，不能写成抽象的“跨学科能力、执行力、工程能力”。
- 论证必须参考用户此前让助手制作个人 PPT 的完整对话及其中的贡献边界，而不是只读取 PPT 成品。
- 每项优势应写成：已经核实的经历／产物、可以立即完成的研究工作、它减少的首年风险，以及仍未证明的部分。
- LCCA、PolyPresentation、全栈排障、多模态研究和严格核验个人贡献可支持问题发现、数据链理解和实验基础设施能力；不能据此声称提出的方法已经有效或已有论文结果。

## 8. 用户推动形成的选题收敛

- 用户首先认可“多模态 Agent 的干预式故障诊断”，并要求独立 proposal 与论证文档。
- 用户随后质疑其与跨模态因果证据溯源是否本来就是前后两步，并要求尝试拼接两者。
- 用户再指出“干预式”作为总立意过窄，推动总题目提升为“证据认知—主动验证”闭环，其中干预式诊断只是方法族之一。
- 用户要求工具漂移下的技能持续修复也形成独立 proposal 与 Markdown，并持续用直接近邻收窄主张。
- 用户始终要求把候选方向当作可被文献和首轮实验杀死的研究假设，而不是为写 proposal 预设它们必然成立。
